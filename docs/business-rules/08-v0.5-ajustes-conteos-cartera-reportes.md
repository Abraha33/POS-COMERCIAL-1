## Inventario: ajustes y conteos
| ID | Regla |
|----|-------|
| BR-AJU-01 | Ajuste manual: `quantity` entero con signo ≠ 0 y `reason` obligatorio. Genera un movimiento `ajuste` (BR-INV-06) con referencia `Ajuste: <motivo>`. |
| BR-AJU-02 | Un ajuste que deja la existencia en 0 o más **resuelve** las alertas `STOCK_NEGATIVE` del producto y la sede (BR-INV-02). Si sigue negativa, la alerta permanece. |
| BR-AJU-03 | El ajuste no puede dejar la existencia por debajo de 0 (`STOCK_INSUFFICIENT`, 409). El stock negativo solo nace de una venta autorizada (BR-VEN-05/13). |
| BR-AJU-04 | El bodeguero solo ajusta o cuenta en **su** sede; `admin` y `propietario` en cualquiera (`FORBIDDEN`, 403). |
| BR-CNT-01 | Conteo: por línea se envía lo contado; el servidor compara con la existencia del sistema (`difference = counted − systemQuantity`) y devuelve todas las líneas. |
| BR-CNT-02 | Cada línea con diferencia ≠ 0 genera un movimiento `ajuste` (referencia `Conteo CNT-xxxx`) y puede resolver alertas como en BR-AJU-02; las de diferencia 0 no generan movimiento. |
| BR-CNT-03 | Un producto no puede repetirse en un conteo (422). Conteo parcial por sede: solo se ajusta lo contado. |

## Cartera: abono con imputación automática y derivados
| ID | Regla |
|----|-------|
| BR-CAR-04 | `POST /customers/{id}/payments`: el abono se aplica a las facturas abiertas **más antiguas primero** (`issued`, luego `due`, luego id; BR-CLI-05) y crea un registro de abono por factura afectada. Supera el saldo total → `PAYMENT_EXCEEDS_BALANCE`. El abono a una factura indicada (BR-CAR-01) se conserva. |
| BR-CAR-05 | Cada abono queda en el historial de la factura (`GET /receivables/{id}/payments`, más reciente primero). Las anulaciones de abono no existen (no modeladas). |
| BR-CAR-06 | Derivados del servidor (el cliente no los recalcula como autoridad): `balance = amount − paid`; `daysOverdue` = días desde `due` (0 si no vence o está pagada); `status`: `pagada` (saldo 0), `vigente` (no vencida), `en_gracia` (1–3 días, BR-CLI-06), `vencida` (más de 3). |
| BR-CAR-07 | Las cuentas por pagar no tienen gracia (**PROPUESTA**): `status` ∈ `vigente`, `vencida`, `pagada`; `daysOverdue` igual que en cobrar. |
| BR-CAR-08 | `Customer.outstandingBalance` = Σ saldos de sus facturas abiertas; `overdueBalance` = Σ saldos de las `vencida` (fuera de gracia, la mora que bloquea crédito, BR-CLI-06). |
| BR-CAR-09 | `Receivable.branchId` y `Payable.branchId`: sede de la venta que origina la cuenta por cobrar / sede que recibe la orden que origina la por pagar (BR-GEN-10). |
| BR-CAR-03 | (SUP, sin cambio) un abono en efectivo no afecta el turno de caja. Sigue pendiente de decisión del dueño. |

## Reportes agregados (solo `reports.view`)
| ID | Regla |
|----|-------|
| BR-REP-01 | `GET /reports/sales-summary?from&to&branchId`: fechas inclusivas sobre `Sale.date`; excluye anuladas (se cuentan en `voidedCount`). `grossTotal` = Σ `total`; `returnsTotal` = Σ devoluciones de esas ventas; `netTotal = grossTotal − returnsTotal`; `averageTicket = round(grossTotal / salesCount)`. `byPaymentMethod` descuenta el cambio del efectivo (BR-VEN-08); `topProducts` = 5 por valor. |
| BR-REP-02 | `GET /reports/aging?asOf&branchId`: saldos abiertos por tramo de días vencidos a `asOf` (por defecto hoy): `current` (no vencida), `d1_30`, `d31_60`, `d61_90`, `d90_plus`. La gracia no cambia el tramo (se cuenta desde `due`). |
| BR-REP-03 | `GET /reports/inventory-valuation?branchId`: valor = max(existencia, 0) × costo unitario. `costBasis` declara el costo usado. **Brecha:** BR-INV-05 pide costo promedio ponderado **por sede**; el modelo hoy solo tiene `Product.cost` y el mock responde `product_cost`. El backend real debe devolver `branch_weighted_average`. |
| BR-REP-04 | `GET /pos/shifts?from&to&branchId` (historial de turnos): fecha de apertura inclusiva. `reports.view` ve todos; el cajero solo los propios; el resto, `FORBIDDEN`. |
